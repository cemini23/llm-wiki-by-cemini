## Narrative

Exqutor targets a concrete failure in vector-augmented analytical queries (VAQs) — SQL queries that mix relational joins/filters/aggregates with vector similarity search, the workload produced by table-augmented RAG. The root problem: generalized vector DBs (pgvector, VBASE, DuckDB) estimate the cardinality of a vector-search operator with **fixed heuristic selectivity values** (pgvector 0.333×, VBASE 0.500×, DuckDB 1.000× of table rows), ignoring the query's actual distance threshold and data distribution. Wrong cardinality misleads the optimizer's join order, join type, and scan strategy, producing catastrophically suboptimal plans — especially for vector *range* queries (`embedding <-> q < D`), whose result count is variable and hard to estimate, unlike fixed-cardinality top-k.

Exqutor is a pluggable cardinality-estimation framework with two paths. **ECQO (Exact Cardinality Query Optimization)**: when a vector index (HNSW, IVF) exists, run a lightweight index search *during planning* to obtain the true range-query cardinality; because HNSW search is deterministic under fixed parameters, that count is treated as exact, and the retrieved candidate set is cached and reused at execution time so the ANN search runs only once per query. **Sampling-based estimation**: when no vector index exists, estimate the qualifying-tuple count over a small sample, with adaptive sample-size tuning driven by a momentum-based feedback loop on the Q-error metric, maintaining per-table sample-size state. Integrated into pgvector, VBASE, and DuckDB via planner hooks, Exqutor delivers (on TPC-H/TPC-DS-derived VAQ benchmarks with DEEP/SIFT/SimSearchNet++ embeddings) ECQO speedups of 1.01× up to **four orders of magnitude** on PostgreSQL-based systems and 1.5×–37.2× on DuckDB, plus 1.2×–3.2× for the index-free sampling path, all with negligible planning overhead.

**Cemini relevance**: As the librarian's kb-server moves toward hybrid retrieval (vector similarity + structured metadata filters/joins over wiki entities), Exqutor's cardinality-estimation fix is exactly the optimizer pathology that would silently degrade those queries on pgvector. It connects to the K47 retrieval-scaling work as the query-planning counterpart to the index-architecture question raised by pvg5.
