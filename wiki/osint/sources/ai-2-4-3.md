## Narrative

**[DEEP-READ — 2026-05-01] K20.** Systematic taxonomy of 190 security advisories filed against the OpenClaw AI agent framework (200K+ GitHub stars). Two-axis taxonomy: **system axis** (10 architectural layers) × **attack axis** (7 adversarial techniques). Introduces a novel "Context Manipulation" kill-chain stage with no analog in MITRE ATT&CK. Three structural root causes identified: pervasive closed-world assumptions, absence of unified inter-layer policy enforcement, and plugin/skill distribution as an ungoverned execution surface. The natural companion to K19's SAE defense paper: K19 provides the execution-contract defense; K20 catalogs the 190-advisory threat model that defense must address.

### Framework architecture (§2)

OpenClaw's runtime comprises seven components: **Channel System** (15 platform adapters — Slack, Discord, Telegram, etc.), **Gateway** (WebSocket API server + Node.js host runtime), **Plugins & Skills** (community marketplace, clawhub.ai), **Agent Runtime** (session management + inter-agent communication), **Memory & Knowledge** (persistent context + vector store), **LLM Provider** (multi-model abstraction), and **Local Execution** (3-phase exec policy pipeline: pre-execution approval → safeBins flag allowlist → sandbox isolation). The exec policy pipeline is the load-bearing security boundary: it must correctly approve, constrain, and isolate every system action an LLM requests.

### Corpus overview (§3)

190 advisories filed in two waves: Wave 1 (Jan 31–Feb 16, 2026: 73 advisories) and Wave 2 (Feb 18–25: 117). Exec Policy Engine dominates by volume (46, 24.2%); Gateway WebSocket leads in severity (highest High-severity count). Severity distribution: Critical 4, High 42, Medium 98, Low 46.

### Two-axis taxonomy (§4)

**System axis** — 10 architectural layers: Channel Input Interface, Plugin & Skill System, Agent Context Window, Gateway WebSocket Interface, Tool Dispatch Interface, Exec Policy Engine, Container Boundary/Host OS, LLM Provider Interface, Inter-Agent Communication, Knowledge & Memory Store.

**Attack axis** — 7 techniques: Allowlist Bypass (37), Injection (28), Privilege Escalation (22), Authorization Bypass (19), Information Disclosure (16), Resource Exhaustion (12), Configuration Manipulation (8). The remaining 48 advisories are hybrid (span ≥2 techniques).

**Kill chain** — 6 stages: Initial Access → **Context Manipulation** (novel — no MITRE ATT&CK analog) → Execution → Credential Access → Privilege Escalation → Impact. Context Manipulation is the stage where attacker-controlled data enters the LLM context window and is processed as instruction — the bridge between external data and internal control that conventional kill chains don't model.

### Channel input interface (§5.1)

35 advisories across 15 platforms. Three sub-patterns: (1) **allowlist bypass via mutable identity fields** — Nextcloud Talk display-name spoofing (GHSA-r5h9), Telegram @username authorization (GHSA-mj5r), Google Chat sender display name (GHSA-chm2). Root cause: identity fields used for policy evaluation are mutable at the platform level. (2) **Webhook auth failure** — missing or incorrectly validated HMAC signatures. (3) **Credential disclosure** — tokens and API keys logged or returned in error responses.

### Plugin & skill system (§5.2)

The **yahoofinance malicious skill** (GHSA-5675) is the headline finding: a two-stage dropper distributed via clawhub.ai that operated entirely within the LLM context window. Stage 1: SKILL.md lure (legitimate-looking market data prompts). Stage 2: platform-differentiated payload — Windows: AES-CBC-encrypted PowerShell blobs; macOS: base64-encoded bash dropper writing to `~/Library/LaunchAgents/`. The skill **bypassed the entire exec policy pipeline** because it never invoked `system.run` — it persuaded the LLM to emit the payload as text, then used social engineering against the operator to execute it. This is a supply-chain attack where the attack surface is the context window, not the exec boundary.

### Agent context window (§5.3)

Four indirect injection advisories: Slack channel metadata prepended to system prompt (GHSA-782p), Sentry error headers included verbatim in context (GHSA-c9gv), resource link `name` fields displayed as agent memory (GHSA-j4hw), filesystem path components resolved into workspace context (GHSA-m8vc). Uniform structural cause: data paths terminating in the context window were designed as information channels without adversarial consideration.

### Gateway WebSocket interface (§5.4)

Three-stage RCE chain (Critical): (1) **gatewayUrl SSRF** (GHSA-g8p2) — attacker-controlled `gatewayUrl` parameter accepted any URL; IPv4-mapped IPv6 (`::ffff:169.254.x.x`), ISATAP, and special-use ranges evaded the SSRF guard. (2) **Token exfiltration** — the SSRF'd WebSocket connection leaked the session auth token to the attacker's server. (3) **node.invoke exec approval bypass** (GHSA-gv46) — `system.execApprovals.set` was reachable via `node.invoke`, allowing the attacker to rewrite the exec allowlist and execute arbitrary commands on the Node.js host. Three independently moderate-severity advisories composed into unauthenticated RCE.

### Tool dispatch interface (§5.5)

57 advisories across three sub-surfaces:
- **File & Process** (30): path traversal in workspace file operations, command injection via unsanitized filenames, TOCTOU races in tempfile creation
- **Sandbox** (17): Docker bind-mount escape (§5.7), unauthenticated noVNC exposure (GHSA-h9g4), workspace-boundary violations
- **Browser** (10): unauthenticated CDP relay endpoints, path traversal in file upload/download, absent CSRF protection. Six of ten High severity: unauthenticated browser access = full agent compromise.

### Exec policy engine (§5.6)

Three allowlist bypasses sharing a single root cause — **lexical model vs. semantic reality**:

1. **Line-continuation bypass** (GHSA-9868): `\n` and `\r` were recognized as escape characters in the shell parser, allowing `echo "ok$\n(id -u)"` to execute `id -u` via POSIX line continuation. Fix: remove `\n`/`\r` from escape set + add `hasShellLineContinuation` pre-check.

2. **Busybox/Toybox multiplexer bypass** (GHSA-gwqp): `busybox` and `toybox` were not recognized as dispatch wrappers. Invoking `busybox sh -c 'whoami'` persisted the `busybox` binary path; subsequent `busybox sh -c '<arbitrary>'` executed without approval. Fix required a new module (`exec-wrapper-resolution.ts`) with a discriminated union result type — `not-wrapper | blocked | unwrapped`.

3. **GNU long-option abbreviation bypass** (GHSA-3c6h): GNU getopt accepts unambiguous prefix abbreviations (`--compress-prog` = `--compress-program`). The denied-flag check used exact set membership; abbreviated flags fell through. Fix: `resolveCanonicalLongFlag` with GNU-style prefix matching.

The root cause: the exec allowlist was a string-matching system operating on static command representations, while the actual security boundary requires reasoning about **command semantics** — how the shell interprets the string, what executable the invocation dispatches to, and what the effective flag set is after abbreviation expansion.

### Container boundary & host OS (§5.7)

Docker sandbox escape via bind-mount injection (GHSA-w235). The `binds` field from `SandboxDockerConfig` was passed verbatim to Docker CLI args without validation. Attack: inject `binds: ["/var/run/docker.sock:/var/run/docker.sock"]` → container gains Docker API access → launch privileged containers → host escape. Also exploitable via `network: "host"`, `seccompProfile: "unconfined"`, `appArmorProfile: "unconfined"`. Fix: +691/−6 lines, new `validate-sandbox-security.ts` (208 lines) with blocked host paths denylist and ancestor-coverage check. Key insight: isolation was emergent from Docker defaults, not from deliberate enforcement — the framework leaned on Docker to behave safely if not told otherwise.

### LLM provider interface & inter-agent communication (§5.8)

Six advisories defining a third bypass class distinct from exec-policy bypass and skill escalation:

**Indirect prompt injection** (4 advisories): data paths terminating in the context window were treated as information channels, not instruction channels. This is the correct assumption for non-LLM systems; it is incorrect when the context window IS the program.

**Inter-session context contamination** (GHSA-w5c7): `sessions send` routes agent→agent prompts stored as `role: "user"`. The model cannot distinguish "end user issued this" from "another agent issued this." Fix: new `input-provenance.ts` with 3-value closed enum — `external_user`, `inter_session`, `internal_system`. Provenance persisted on message; `sanitizeSessionHistory` prepends `[Inter-session message]` annotation; memory hook skips inter-session turns.

**Structural analysis**: Three bypass classes operate at different levels relative to the reasoning layer:
- Exec-policy bypass: **below** the reasoning layer (circumvents enforcement of permitted system calls)
- Skill escalation: **beside** the reasoning layer (registers malicious capabilities before policy is applied)
- Prompt injection: **above** both (manipulates intent before any policy enforcement is reached)

### Defense recommendations (§6)

Six defense areas mapped to taxonomy branches:

| Defense area | Target | Key recommendation |
|---|---|---|
| §6.1 Channel integration | 13 allowlist-auth bypasses | Key allowlists on immutable platform IDs (numeric UID, OAuth `sub` claim), not display names |
| §6.2 Gateway & API | Gateway RCE chain | Runtime-constructed allowlist of legitimate gateway URLs; exclude `system.execApprovals.*` from `node.invoke` dispatch |
| §6.3 Exec allowlist | 3 lexical bypasses | Semantic interpreter, not string-matching; or restrict to direct-argv mode (no shell wrapper) |
| §6.4 Sandbox | Docker escape | Mandatory validation module at container creation; defense-in-depth that constrains worst-case outcome of any config compromise |
| §6.5 Plugin/skill distribution | yahoofinance supply chain | Content review + cryptographic signing + context-window provenance annotations |
| §6.6 Agent/prompt runtime | Prompt injection | Generalize 3-level provenance to mandatory provenance tag for every string entering context window |
| §6.7 Cross-cutting | Inter-layer composition | Typed, validated, provenance-carrying request objects at every inter-layer interface |

### Three structural conditions (§7)

1. **Pervasive closed-world assumption**: each subsystem implemented as though inputs originate from a cooperative, finite, trusted set of sources. The exec allowlist assumed commands are enumerable via lexical parsing. Channel allowlists assumed identity fields are immutable. Context assembly assumed strings are information, not instruction. Defensible in closed systems; invalid in OpenClaw's open-world deployment model.

2. **Absence of unified inter-layer policy enforcement**: trust decisions made locally (per call site, per subsystem, per handler) without a global invariant enforced across component boundaries. The Gateway RCE chain is the existence proof: three independently moderate-severity advisories composed into unauthenticated RCE because no enforcement point observed the full call path from LLM tool invocation to Node-Host shell execution.

3. **Plugin/skill distribution as execution surface**: the yahoofinance skill did not exploit a memory-safety bug or parsing flaw — it operated entirely within the LLM context window, evading the entire exec policy pipeline. The runtime provides no dedicated policy primitive for the distribution channel.

### Cemini relevance

K20 is the natural companion to K19 (SAE). Where K19 provides the execution-contract defense, K20 catalogs the 190-advisory threat model that defense must address. The mapping is direct:

| K20 finding | SAE mitigation | Coverage |
|---|---|---|
| Exec allowlist lexical bypasses (§5.6) | M1 (Intended Policy Spec + hard OOS rules) + M3 (projection enforcement) | Semantic, not lexical |
| Gateway RCE chain (§5.4) | M1 + M6 (auditability — full call-path visibility) | Inter-layer composition |
| yahoofinance supply chain (§5.2) | M2 (trust-state conditioned budgeting — provenance score) + M5 (staged execution) | Distribution → execution boundary |
| Prompt injection (§5.3, §5.8) | M2 (I_inj flag from safety monitors) | Context provenance |
| Docker sandbox escape (§5.7) | M1 (capability allowlists) + M4 (cooldown/rate limits) | Configuration integrity |
| Inter-session contamination (§5.8) | M2 (z_t provenance scoring — inter_session < external_user) | Origin-gated trust |

K20's §6.7 "unified inter-layer policy enforcement via typed, validated, provenance-carrying request objects" is essentially the architectural specification for SAE's ExecutionRequest/ExecutionContext/ExecutionDecision API contract. K20's §6.6 "mandatory provenance tag for every string entering the context window" is the context-window analog of SAE's trust-state (z_t) for execution actions. The two papers, read together, define a complete execution-security architecture: K20 identifies the attack surface and structural conditions; K19 provides the enforcement primitive.

## Snippets

**S1 — The closed-world assumption (p.26, §7)**:
> "The first structural condition is a pervasive closed-world assumption: each subsystem was implemented as though its inputs originated from a cooperative, finite, and trusted set of sources. The exec allowlist assumed that command representations were enumerable through lexical parsing [8, 9, 10]. Channel allowlists assumed that sender identity fields were immutable properties of authenticated sessions [14, 15]. The LLM context assembly pipeline assumed that strings entering the context window represented information rather than potential instructions. Such assumptions are defensible in closed systems; OpenClaw's open-world deployment model invalidates each of them."
>
> *— ai-2-4-3.pdf p.26, §7. The core architectural insight: every subsystem trusted its inputs by default.*

**S2 — Lexical model vs. semantic reality (p.20, §5.6.4)**:
> "Taken together, these three bugs share a single root cause: the exec allowlist was designed as a string-matching system operating on static representations of command text, while the actual security boundary it was meant to enforce requires reasoning about command semantics—how the shell will interpret the string at runtime, what executable the invocation will actually dispatch to, and what the effective set of active options will be after GNU abbreviation expansion."
>
> *— ai-2-4-3.pdf p.20, §5.6.4. The root cause of all three exec allowlist bypasses.*

**S3 — Three bypass classes relative to the reasoning layer (p.23, §5.8.3)**:
> "Exec-policy bypass operates below the reasoning layer—it circumvents the runtime's enforcement of which system calls or tool invocations are permitted. Skill-level escalation operates beside the reasoning layer—it exploits the operator trust model to register malicious capabilities before policy is applied. Prompt injection operates above both—it manipulates the content from which the model constructs its intentions before any policy enforcement is reached. A model that has been successfully prompt-injected may voluntarily invoke a tool that policy would otherwise have denied, rendering the policy irrelevant without ever triggering it."
>
> *— ai-2-4-3.pdf pp.23–24, §5.8.3. The three-tier model of policy bypass relative to the LLM reasoning layer.*

**S4 — Context Manipulation as novel kill-chain stage (p.10, §4.3)**:
> "The Context Manipulation stage has no direct analog in the conventional Cyber Kill Chain or MITRE ATT&CK frameworks. It captures the unique property of LLM-integrated systems where attacker-controlled data enters the model's context window and is processed as instruction rather than as data. Traditional kill chains model data as passive—something to be exfiltrated or encrypted. In agent frameworks, data is active: it can persuade, redirect, and reprogram."
>
> *— ai-2-4-3.pdf p.10, §4.3. The novel kill-chain stage specific to LLM-agent threat modeling.*

**S5 — yahoofinance as supply-chain execution surface (p.15, §5.2)**:
> "The skill operated entirely within the LLM context window and bypassed all runtime policy enforcement. The SKILL.md file contained no executable code, no shell commands, and no tool invocations. It consisted entirely of natural-language instructions that, when processed by the LLM, caused the model to emit the attacker's payload as part of its response and then socially engineer the human operator into executing it. The exec policy pipeline never saw a command to evaluate."
>
> *— ai-2-4-3.pdf p.15, §5.2. The yahoofinance malicious skill as a supply-chain attack that operates above the exec policy layer.*

**S6 — Gateway RCE chain composition (p.17, §5.4)**:
> "The three-step Gateway RCE chain illustrates the consequence of absent inter-layer policy enforcement: the SSRF vulnerability (gatewayUrl) was filed as a Medium-severity information disclosure; the token exfiltration was the natural consequence; and the node.invoke exec approval bypass was filed separately. None of the three advisories was individually Critical. Composed together, they yielded unauthenticated remote code execution on the Node.js host."
>
> *— ai-2-4-3.pdf p.17, §5.4. The composition problem: individually moderate advisories composing into Critical.*

**S7 — Sandbox isolation as emergent, not enforced (p.21, §5.7)**:
> "The +691/−6 line count reveals a structural truth about the original sandbox design: the isolation guarantee was entirely emergent from Docker's own defaults, not from any deliberate enforcement by OpenClaw. The framework leaned on Docker to behave safely if not told otherwise, but provided no barrier against configuration that explicitly opted out of protection."
>
> *— ai-2-4-3.pdf p.21, §5.7. Sandbox isolation as emergent property, not deliberate enforcement.*

**S8 — Unified inter-layer enforcement (p.26, §6.7)**:
> "All five defense areas above share a common structural requirement: trust properties must be enforced at inter-layer interfaces through typed, validated, provenance-carrying request objects, rather than at per-call-site checks within each layer. A unified policy boundary would evaluate, for any node.invoke frame, whether the initiating context (agent, operator, inter-session) is authorized to request the specific command with the specific parameters, regardless of which individual layer the request traverses."
>
> *— ai-2-4-3.pdf p.26, §6.7. The architectural specification for what SAE's ExecutionRequest/ExecutionContext/ExecutionDecision contract provides.*

**S9 — Context provenance as security boundary (p.25–26, §6.6)**:
> "We propose generalizing this into a mandatory provenance tag for every string entering the context window, including those from channel metadata, skill files, and tool outputs. By integrating existing detection-based defenses with this architectural metadata, the runtime can condition tool-call authorization on the verified origin of an instruction rather than its lexical content alone. This transformation shifts the context window from a passive information channel into a monitored, provenance-aware instruction surface."
>
> *— ai-2-4-3.pdf pp.25–26, §6.6. Context provenance as the generalization of §5.8's inter-session fix.*

**S10 — Future direction (p.27, §7)**:
> "Securing AI agent frameworks is not primarily a matter of enumerating and patching vulnerabilities; it is a matter of designing a coherent trust model that remains sound when the layers of the system are composed in the manner an adversary will inevitably treat as a single unified attack surface. Our two-axis taxonomy presented in this paper provides the vocabulary for that design conversation."
>
> *— ai-2-4-3.pdf p.27, §7. The paper's closing thesis: taxonomy as vocabulary for trust-model design.*
